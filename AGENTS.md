# AGENTS.md

## Контекст проекта

Мы строим локальное веб-приложение на Go для личной базы знаний.

Пользователь вводит текст через web UI, backend сохраняет исходное сообщение в SQLite, создаёт processing job, worker классифицирует сообщение через mock/AI classifier, а результат попадает либо в `knowledge_items`, либо в `unknown_items`.

Главный pipeline первой версии:

```text
raw text -> processing job -> classification -> knowledge/unknown
```

SQLite — главный источник правды. Все важные данные должны храниться в SQLite. Markdown/Obsidian и vector index в будущем являются только производными представлениями, которые можно пересобрать из SQLite.

На текущем этапе не делаем Telegram, Obsidian export, vector search, voice, documents, agents, Redis, Kafka, Postgres и сложную архитектуру.

## Правила

1. Не изобретать велосипед: писать короткий и простой код, не плодить функции, слои и абстракции там, где в этом нет необходимости.
2. Предпочитать стандартную библиотеку и уже добавленные зависимости новым пакетам.
3. Не усложнять архитектуру раньше времени.
4. SQLite остаётся единственным обязательным хранилищем и source of truth.
5. Все исходные сообщения сохранять без изменений.
6. AI не должен напрямую писать в базу: AI возвращает JSON, backend валидирует результат и только потом пишет данные.
7. Если результат классификации невалидный, неполный или confidence низкий, сохранять сообщение в `unknown_items`.
8. Любая обработка должна быть перезапускаемой.
9. Для Go-кода использовать idiomatic Go: явные ошибки, простые структуры, `context.Context` для request/IO/goroutine lifetimes, `gofmt`.
10. После изменений запускать релевантные проверки: минимум `gofmt`, `go test ./...`, при необходимости `go vet ./...`.

## Рабочий пайплайн при написании кода

1. Сначала коротко описать план изменений: что будет изменено, в каких слоях/файлах и какие есть риски.
2. Дождаться, что план понятен в рамках запроса, и только после этого переходить к реализации.
3. Делать минимальные изменения строго в рамках согласованного плана.
4. После реализации запустить релевантные проверки и кратко описать результат.
